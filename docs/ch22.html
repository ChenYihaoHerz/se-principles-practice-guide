系统安全工程

Systems Security Engineering

这里的“安全”指防范蓄意攻击、滥用和泄密（security），与防止事故的安全性（safety）不同。系统安全工程（Systems Security Engineering, SSE）是系统工程的一个专门领域，与系统开发的其他工作相辅相成。它起源于美国国防部、国土安全部门和执法部门：这些部门开发的许多系统要求安全地运行，要接触敏感数据，还牵涉国家安全和个人安全。

常被引用的定义来自美国国防部的一份军用手册：系统安全工程是系统工程的一个组成部分，运用科学和工程原理找出系统在安全方面的薄弱环节，并尽量减少或控制与这些薄弱环节有关的风险；它借助数学、物理和相关的科学学科，以及工程设计和分析的原理和方法，来规定、预测和评价系统在安全威胁面前的脆弱程度。其他来源把定义扩展到防止对系统的滥用和恶意行为，以及保护敏感的数据、流程、技术和知识产权。无论采用哪一种定义，系统安全工程的做法都是在开发中的系统概念上加强安全。

系统安全工程师做什么

系统安全工程师要能够从整体上、从多个角度看待系统的安全措施、薄弱环节、风险和机会，才能形成全面而充分的安全防护能力。系统安全工程师要和系统工程团队的其他成员一样，在开发初期就编写大量系统工程文档，并在给定的开发进度之内把安全能力集成进来；还要像做其他设计权衡一样做安全方面的权衡分析，让系统的领导层看清加入某项安全能力会带来什么后果。

安全措施也有代价，有时会和其他设计目标相冲突：为了安全可能要牺牲效率，还可能带来访问上的限制、设计灵活性的下降，以及额外的测试和运行约束。所以安全措施要用得审慎，例如不能让安全检查拖慢对时间要求很高的计算。

为什么越来越需要系统安全工程

在国防领域，许多对手一心要打败正在开发的系统。有的直接下手，通过与系统及其接口的直接交互来破坏或削弱系统原有的能力；有的间接下手，例如污染供应链，在开发过程中植入恶意的程序，使对手可以在自己方便的时候削弱系统，而这个时候往往正是关键的行动期间。美国国防部提出了加强系统安全工程的三个动因：

  • 系统越来越依赖商业技术；
  • 供应链容易受到污染；
  • 系统的复杂程度和相互连接程度越来越高。

非国防领域也有同样的担忧：

  • 现代汽车的微处理器中已经有超过 1.5 亿行代码；汽车与维修、营销等外部机构之间越来越多的连接，增加了受到恶意攻击的风险。
  • 不经人工干预就与外部网络交互的自动化系统尤其脆弱；靠语音甚至意念来启动、用来查询信息和操控技术设备的系统，也是滥用者眼中的绝佳目标。
  • 医疗和金融机构特别关心数据的完整性和隐私不受侵犯。

安全问题也不只出在计算机、网络和软件上：薄弱环节会迅速形成，对基础设施、隐私以及现有和计划中系统的生存能力造成严重破坏。对手能力很强，常常同时动用多种技术手段，找出看似微小、却足以让系统瘫痪的弱点；系统本身的高度复杂，如果没有充分考虑安全，也会增加薄弱环节。威胁一方往往占有不对称的优势，因此防御要贯穿整个生命周期，要能够迅速评估，防御手段也要集成到运行中的系统里。所以安全措施必须集成到系统的设计之中，从需求阶段开始，一直到报废处置都是如此。

从整体看系统：上下文图和七个问题

系统安全工程师要用挑剔的眼光审视开发中的系统概念，找出那些可能严重影响系统运行的关键部分，无论问题出在内部的功能上，还是出在与其他系统、人员或组织的外部接口上。仔细回顾以往的薄弱环节和威胁、请安全专家参与、采用降低风险的做法，都会使安全与系统工程结合得更好。

借助这张图，可以对系统提出七个问题：

  • 最关键的功能是什么？如果这些功能遭到篡改或降级，系统还能完成任务吗？
  • 最关键的接口是什么？
    • 如果这些接口连不上，或者不能成功传送所需的信息、产生预期的效果，系统还能正常运行吗？
    • 对依赖这些接口的其他系统和组织有什么影响？
  • 系统的访问情况如何？
    • 访问是完全开放还是受到控制，有没有办法绕过访问控制？
    • 在系统某一部分获得授权的用户，能不能进入本无权进入的其余部分？进去以后能执行哪些命令和操作，会造成什么影响？
    • 如果用户无意中执行了错误的命令，系统会怎样反应？
  • 物理防护如何？直接控制系统的区域、维修接入口或数据存放处，会不会让没有授权的人随意接触？
  • 数据处于什么状态？
    • 存放在系统中的数据有没有适当的保护？
    • 从一个系统传往另一个系统的数据又如何？
  • 公开来源里有什么？
    • 系统关键功能的资料，能不能从公开来源或公共场所轻易得到？
    • 关键的运行细节，会不会让没有权限、也不需要知道的人看到？
  • 关键部件得到保护了吗？
    • 需要额外防护的关键部件有没有找出来，防护是否充分？
    • 有没有发现恶意活动的手段，发现以后有没有足够的应对措施？
    • 万一遭到恶意攻击，有没有充分的恢复计划？

需要分析的几类安全问题

  • 关键功能分析：功能分解有助于找出对整个系统运行影响重大的关键功能。还可以设定某些功能在功能流程的不同阶段降级，再做运行分析，找出需要保护或加固的功能以及功能组合。系统安全工程师可以凭自己的安全知识判断功能的关键程度，必要时请熟悉系统工作方式的人协助。
  • 关键接口分析：今天的系统越来越多地互相连接，要靠外部交互才能完成任务。
    • 用时序图分析接口和交互的先后顺序，可以找出依赖外部系统的关键环节。
    • 可以查询系统建模语言的模型，例如找出某个信号的全部用途，或者它可能经过的每一个接口，再用表格或矩阵显示查询结果。
    • 了解系统和操作人员对经过接口传来的正确或错误数据会作出什么反应，可以看出接口有多重要。
    • 必要时根据接口的关键程度和对依赖对象的信任程度，另找备用的接口或数据来源。
  • 系统访问：
    • 许多安全人员只盯着企图闯进系统的外部恶意人员，系统安全工程还要考虑已经在系统内部、正在操作系统的内部威胁（insider threat）。任何用户不受限制的访问，无论有意还是无意，都可能危及系统运行。
    • 要考虑操作、维修、测试和管理等所有角色，弄清每个角色以什么身份、在什么层级访问系统，按角色分配权限。
    • 用户从一个已经获得授权的入口在系统中横向移动，可能造成损害。
    • 红队（red team）擅长发现决策者看不到的访问途径。
  • 物理安全：数据中心、用户终端、维修接入口等都需要物理防护。人们往往以为外层屏障已经足够，于是安全边界以内的区域常常不上锁或敞开着，这正好给了攻击者可乘之机。系统安全工程师要和负责物理安全的官员一起，找出系统边界之内（包括合作的组织和系统）容易接近的地方，加以加固。
  • 数据安全：数据分为三种状态，分别保护。
    • 存储中的数据放在数据库、数据仓库、档案、磁带和备份里，要防止未经授权的处理、查看和使用。
    • 传输中的数据要防止被截获或篡改，可以采用网络安全方案、数据保护方案和加密协议。
    • 到了用户手里、正在使用的数据，要防止未经授权的复制、修改、删除等恶意操作，办法包括可靠的用户身份认证、身份管理和权限配置。
    • 完善的培训计划和对安全状况的持续监视，也是成功的安全工作不可缺少的。
  • 运行保密（Operational Security, OPSEC）：
    • 只有确实“需要知道”的授权用户，才能接触系统的关键功能和运行情况。
    • 即使看似无关的信息，例如即将进行的试验，或者对其他机构服务的依赖越来越大，也可能提醒对手去寻找别的攻击途径。最好的安全措施，也可能因为有人在外面谈论关键信息而全部失效。
    • 开发和运行期间都要评估系统对外暴露的痕迹；红队可以在互联网和网上论坛搜集公开情报，看看能否发现有关键项目正在开发。
  • 安全框架：参照美国国家标准与技术研究院的网络安全框架（NIST Cybersecurity Framework），安全工作分为五个步骤。
    • 识别：找出系统中需要保护的关键节点。
    • 保护：用现有的防护技术和方法保护这些节点。
    • 检测：借助刚刚部署的防御手段，检测和监视针对系统的恶意活动。
    • 防御：系统一旦遭到攻击，就击退恶意行动、阻止进一步的破坏。这一步在该框架的正式文本中称为“响应”。
    • 恢复：系统一旦受损，就恢复到可以接受的运行状态，恢复关键能力，让用户能够继续使用。

详解：安全工作贯穿系统工程的每一步

系统安全工程师要和团队的其他成员一起提出安全需求，确定安全功能和设计，构建系统要实现的架构，在开发和集成阶段把安全能力纳入系统，最后在安装和测试阶段执行安全测试。把安全工作对应到四步系统工程方法上，可以看到需求分析、功能定义、物理定义和设计验证每一步都有相应的安全工作，测试只是其中的最后一步。

系统交付以后，安全工作还要继续：

  • 供应链中的安全：保障阶段要通过供应链继续评估系统。有缺陷的备件和更新可能降低系统性能；受到污染的供应链还可能让故障一直潜伏，直到需要执行关键操作或关键命令时才发作。系统定期维修以及长期的升级改进期间，都要检查是否采取了足够的措施。
  • 运行和维修阶段的安全：对部署计划和运行手段实行运行保密；对系统本身、保障部件、设施，以及为系统提供服务的操作人员和供应商人员（其中可能有第三方厂商和外国的支持机构）实行物理安全；对外公开发布的信息要先检查，以免无意中泄露系统的能力和局限。
  • 报废阶段的安全：要确保系统报废以后，没有残留的信息、数据或技术可以让“拾荒者”从中提取出来。这意味着要清除或销毁信息系统的存储器，保护那些可能泄露情报、或者让人仿制出企业和制造秘密的物理部件，处理好运行和维修程序方面的文档，并对相关人员做好离岗交代，提醒相关人员不要泄露专有或保密的信息。

不同领域的安全问题

系统安全工程可以叠加到许多需要系统工程的领域上，下面是各领域中一些可能遭受的攻击：

领域可能遭受的攻击
国防干扰传感器；中断卫星下行数据；破坏指挥控制设施
交通利用车辆维修服务的漏洞；伪造车辆之间的通信；发出虚假的交通信号；在通信网络中植入恶意软件
农业篡改农药的配制和分发系统；向作物监测系统注入虚假数据；破坏由计算机控制的灌溉系统
关键基础设施破坏供水设施；破坏配电系统；破坏发电系统
  • 国防和国土安全：要保护关键的、专有的制造配方和独特的作战能力，并在整个使用期间保持这些能力；既要把入侵者挡在系统之外，也要防止内部人员把信息泄露出去。与合作组织或合作国家一起工作时，对方也可能有意或无意地泄露有关系统的敏感信息。
  • 交通：确保交通系统，尤其是公共交通系统，安全而高效地服务于所面向的人群；即使操作人员或乘客企图让系统出故障，系统也要正常工作；还要遵守社会和技术两方面的准则。
  • 农业：保证系统对操作人员和所生产、处理的农产品都是安全的，关注接触食品的化肥和其他化学品的用量，并使系统符合技术和农业方面的法规。
  • 关键基础设施：与交通部门相似，要与相关的政府官员、用户和监管机构合作，了解系统的工作环境，才能把恰当的安全能力用到系统中。

安全的验证与分析

系统安全工程师在团队中的作用与其他成员相似，关注点是系统与外部实体和组织之间接口的安全，以及系统内部处理过程的安全。对外，要了解系统有哪些外部连接，包括权限、访问控制，以及允许或拒绝连接的规则，因为恶意程序可能来自系统之外，经过传送感染系统；对内，要了解运行系统的内部过程和软件过程，确保恶意程序不会因为某种逻辑或安全设置而在无意中激活。

安全测试和分析还要确保安全控制措施不会干扰或削弱系统的运行。整个生命周期中都要安排安全更新：安全补丁既有根据安全研究定期发布的，也有在恶意代码大范围爆发后临时发布的。许多已部署的系统连续运行，很少有机会离线更新安全功能，所以要建立一种办法，定期识别并更新全部在用的系统。

系统安全工程师与系统工程团队其他成员之间的输入和输出大致如下：
