第 16 章

系统集成

Systems Integration

系统集成（Systems Integration）把分别设计制造的组件组装成子系统，再把子系统组装成一个有效运行的整体，并证明它满足全部运行需求。它的目标是证明系统的工程设计可以交付生产，进而投入使用。

如果每一个组件都设计正确、制造无误，集成就会相当简单，可是一组承包商开发一个复杂系统时，这样的条件从来不会完全具备。这是工程化的组件第一次连在一起、作为一个整体工作，含有新研制元素的系统几乎必然会暴露出意料之外的不兼容。到了开发的这个后期阶段，这些问题必须在几天之内解决，不能拖上几周，为此组织的突击攻关应当由系统工程师带领，并与项目经理紧密配合。

按什么顺序组装

集成是分解的逆过程，能否顺利，取决于系统当初划分得好不好。组装时宜采用逐步集成：每次只加入一两个元素，测试通过后再继续。这样做需要用测试设备模拟尚未加入的部分，要多花一些钱，但便于控制整个过程，出了问题也容易诊断，从长远看一再证明是相当划算的。软件也是这样做的：先把主控程序和一些不起作用的“桩模块”连起来，再把桩模块逐个换成真正的模块。

组装的顺序有一条原则：尽量不需要专门制造信号发生器去模拟内部组件。每加入一个组件，它的输入要么来自外部输入的发生器，要么来自已经组装好的组件。所以应当先集成只有外部输入的组件，例如支撑结构、接收外部信号的传感器和电源。

以一个由 A、B、C 三个组件组成的子系统为例，信号依次从 A 传到 B 再传到 C，A 和 C 各有一个外部输入。正确的顺序是先装 A 并测试它的输出，再加入 B，最后加入 C。如果 B 的输出不对，先检查来自 A 的输入是否正确。测试配置中，A 与 B、B 与 C 之间设有内部测试点，一个由 A、B、C 的模型组成的预测模型计算每个测试点应有的输出，用来定位偏差出在哪里。

安全问题、部件暂时缺货、关键部件需要尽早测试等情况，可能要求打破这个理想顺序，这时由系统工程师判断。子系统集成好以后，再按同样的思路把子系统集成为整个系统。在整个系统层面才发现的故障，比在子系统层面发现的更难追查、代价更高。

三种集成方式

选择哪种方式，由系统工程师、项目经理和利益相关者根据目标、进度、预算和期望的结果共同决定。硬件集成还可以串行或并行地进行：

  • 串行集成的每一步都要等前一步成功之后才开始，容易发现错误，但速度受限于每一步本身；
  • 并行集成让几条线同时进行，能缩短总的集成时间，但需要更多的质量保证人力，才能保证错误都被发现。

敏捷开发和体系中的集成

在敏捷开发中，集成在每一个冲刺中持续进行，小项目每天集成一次，大项目每周集成一次。体系的集成则更困难：

  • 组成体系的各个系统就像一个个“黑盒子”，内部情况不透明；
  • 各个系统分属不同的所有者，经费也各自独立，需要额外的协调。
