第 16 章

系统集成

Systems Integration

系统集成（Systems Integration）把分别设计制造的组件组装成子系统，再把子系统组装成一个有效运行的整体，并证明它满足全部运行需求。它的目标是证明系统的工程设计可以交付生产，进而投入使用。在生命周期中，集成与评价阶段从工程设计阶段接过包括各个组件在内的工程样机，交出系统的生产规范和一个经过确认的生产系统设计。

如果每一个组件都设计正确、制造无误，集成和随后的评价就会相当简单。可是当一组承包商在技术迅速发展的时期开发一个复杂系统时，这样的条件从来不会完全具备，所以集成总是复杂而困难的，需要最好的技术团队在系统工程的领导下工作。集成阶段开始时，常常还有大量准备工作没有完成，进度因此往往比原计划慢得多。

集成之所以单独成为一个阶段，是因为它在三个方面与工程设计截然不同：

  • 工作重点：工程设计关注的是单个组件的设计和测试，通常由许多不同的工程组织分别完成；集成关注的是把这些组件组装成一个完整的、能工作的系统。
  • 参与者：主要是系统工程人员和设计工程人员，这些人员代表系统的各种功能和学科，通常按组件和子系统的能力组织起来。
  • 关键问题：这是工程化的组件和子系统第一次连在一起、作为一个整体工作。无论计划和努力多么周到，含有新研制元素的系统在集成时几乎必然会暴露出意料之外的不兼容。到了开发的这个后期阶段，这些问题必须在几天之内解决，不能拖上几周甚至几个月。为此组织的任何突击攻关，都应当由系统工程师带领，并与项目经理紧密配合。

按照系统工程方法，系统的功能设计在前几个阶段已经完成，所以这一阶段的“功能定义”一步针对的是集成设施，“物理定义”一步就是子系统和系统的集成。典型的工作有两项：

  • 通过逐个加入、逐步测试，把测试过的组件集成为子系统，再把子系统集成为完整的系统；
  • 设计和建造集成所需的测试设备和设施，用来支持集成过程并演示端到端的运行。

按什么顺序组装

集成是分解的逆过程，通常分两步完成：先把组件集成为子系统，再把子系统集成为整个系统。集成能否顺利，取决于系统当初划分得好不好：子系统之间的相互作用是否简单，子系统内部是否分成了界限清楚的组件。经验表明，无论各个组件测试得多么彻底，几乎总会留下一些事先没有预料到的不兼容，直到各个元素组装到一起才显现出来。消除这些不兼容通常要修改某些组件，而组件一改，测试设备或测试程序往往也要相应修改，所有相关的文档都要跟着更新。

组装时宜采用逐步集成：每次只加入一两个元素，测试通过后再继续。这样做需要用测试设备模拟尚未加入的部分，要多花一些钱，但便于控制整个过程，出了问题也容易诊断；从长远看，这种做法一再证明是相当划算的。软件也是这样做的：先把主控程序和一些不起作用的“桩模块”连起来，再把桩模块逐个换成真正的模块。组装的先后顺序和每一步之间测试的间隔，由一个专门的系统工程师和测试专家小组决定。

组装的顺序有一条原则：尽量不需要专门制造信号发生器去模拟内部组件。也就是说，每加入一个组件，它的输入要么来自外部输入的发生器，要么来自已经组装好的组件。所以应当先集成只有外部输入的组件，一般是三类：

  • 子系统的支撑结构；
  • 信号或数据的输入组件，例如接收外部控制信号的传感器；
  • 子系统的电源。

以一个由 A、B、C 三个组件组成的子系统为例，信号依次从 A 传到 B 再传到 C，A 和 C 各有一个外部输入。正确的顺序是：先装 A 并测试它的输出；再加入 B，如果 B 的输出不对，先检查来自 A 的输入是否正确；最后加入 C。这个测试配置有三个特点：

  • 一个复合的输入发生器，同时提供送给 A 和送给 C 的两路外部输入；
  • A 与 B、B 与 C 之间设置了内部测试点；
  • 一个由 A、B、C 的模型组成的预测模型，计算每个测试点应有的输出，用来定位偏差出在哪里。

安全问题、部件暂时缺货（这时要用替代品或模拟器代替）、关键部件需要尽早测试等情况，可能要求打破这个理想顺序，这时由系统工程师判断。

子系统集成好以后，再按同样的思路把子系统集成为整个系统。在整个系统层面才发现的故障，比在子系统层面发现的更难追查、代价更高，对项目的影响也更大。系统集成测试设施常常是由各个子系统的测试设施逐步扩建而成的，设计它本身就是一项重要的系统工程任务：它要能接触到系统内部的测试点，还要足够灵活，能适应系统的更新。

三种集成方式

选择哪种方式，由系统工程师、项目经理和利益相关者根据目标、进度、预算和期望的结果共同决定。无论采用哪种方式，组装的次序都可以有三种安排：

  • 按到货的先后：哪个元素先到就先集成哪个；
  • 按预先确定的顺序逐步加入，这更接近自顶向下或自底向上的做法；
  • 按共同的属性分组：例如把可靠性最高或最低、复杂程度最高或风险最大的元素放在一起，组装好的子系统可能因此需要额外的关注。

集成的计划和设施

集成计划要考虑的事情包括：

  • 总体的技术集成计划：在哪里集成、谁参加、做什么、什么时候做；
  • 集成期间足够的质量保证人力；
  • 人员培训；
  • 对分包商的管理，包括相互依赖、质量和接口；
  • 集成过程中的风险评估；
  • 把每一步工作与需求以及即将进行的试验联系起来的审计记录；
  • 根据集成结果评价性能；
  • 设施的地点、把组件和子系统运到上一级集成设施所需的运输方式、需要的技能和人员配备；
  • 设施本身的特殊限制，例如射频屏蔽和供电。

集成是否做得正确，可以对照以下几项检查：

  • 是否按正确的集成计划执行？
  • 时间表是否留出了足够的时间？
  • 所有组件和构型项是否都有交代？
  • 所有接口是否都已识别并经过验证？
  • 所有工具和程序是否都已具备？
  • 所有工作是否都有记录？

集成地点要在系统概念形成的时候就开始考虑，开发者、集成者、测试者、利益相关者、用户和制造商分别在哪里，都会影响这个决定。有时由一个总集成商（Lead Systems Integrator）负责整个集成工作；有时集成的安排并不由系统工程师掌握，例如大型国防项目的零部件分别在许多个州生产，只能按技术上的依赖关系或运输距离，组成地区性或按子系统划分的集成中心。

  • 软件集成设施：软件模块可以在主开发方的场地集成，也可以在各个分包商的场地集成，各方都要遵守共同的接口和计量单位。软件架构规定了接口、单元、模块化程度和逻辑界限，从而决定了需要多少集成工作。
  • 硬件集成设施：送来的子系统或组件先要经过检验和接收，才能进入集成。采用共同的物理接口有利于标准化和集成。
    • 串行集成：每一步都要等前一步成功之后才开始，容易发现错误，但速度受限于每一步本身。
    • 并行集成：几条线同时进行，缩短总的集成时间，但需要更多的质量保证人力，才能保证错误都能发现。
    设计结构矩阵（Design Structure Matrix）能直观地显示组件之间的连接，帮助找出可以先组合在一起的组件。汽车装配就是一个合适的例子：按各个组件的输入和输出重新编排，先把相关的组件组合起来，再与其他子系统集成，装配过程会更有效率。
  • 人因集成设施：国防、航空航天和汽车等行业都要把人的使用纳入集成。汽车厂商会在不同的设施里分别评价自动驾驶、车载娱乐和人体工程方面的设计，看哪些能力和组件的组合效果最好。
    • 参加评价的人员应当熟悉现有的操作，能代表现有使用群体的一般情况，同时了解新系统的能力，能指出新系统让完成任务变得更容易还是更困难。
    • 一小部分人不一定能代表未来的操作人员，从更大的范围里挑选参加评价的人员可以缓解这个问题。
    • 如果操作人员来自陆军、海军、空军等不同军种，或者分别使用水面、航空和水下系统，各方对同一情况的理解可能不同。这时还需要把整个系统连同所有操作人员一起集成，确认每个系统都收到了应有的数据，并且对信息的理解一致。

敏捷开发和体系中的集成

在敏捷开发中，集成在每一个冲刺中持续进行，小项目每天集成一次，大项目每周集成一次。用户因此有许多次机会评价上一个冲刺以来增加的能力并提出反馈；如果某次集成需要增加人手或特别关注，应当在 Scrum 过程中预先计划、安排资源。

体系的集成与单个系统的集成有相同之处：接口仍然很重要，包括计量单位、时序和对信息的理解，计划和人员技能也同样重要。但它更困难：

  • 组成体系的各个系统就像一个个“黑盒子”，内部情况不透明；
  • 各个系统分属不同的所有者，需要额外的协调；
  • 经费也各自独立，影响各个系统响应变化的速度；
  • 大型的跨国项目，还要克服文化、组织和语言上的隔阂。
