试验与评价

Test and Evaluation

试验与评价是揭示一个产品的关键属性、把它们与预期相比较，从而判断它能否进入下一步工作的一系列活动。在集成与评价阶段，试验与评价成为核心工作，最后要在一个逼真复现预定使用环境的条件下评价整个系统。它要回答两个问题：系统是否符合规格？系统是否满足用户的使用需要？只有两者都得到肯定的回答，系统才能投入生产和部署。

与这两个问题对应的是两类试验：由开发方进行的研制试验与评价，用来验证（Verification）系统符合规格，也就是性能、兼容性、可靠性、维修性、可用性和安全等技术要求；由客户或独立机构进行的使用试验与评价（Operational Test and Evaluation），用来确认（Validation）系统满足运行需求本身。研制试验对照的性能规格，是从运行需求转化而来的；使用试验直接检查运行需求。

与工程设计阶段相比，评价阶段有三点不同：

  • 工作重点转向建立一个全面的系统试验环境并评价整个系统。
  • 参与者主要是系统工程、试验工程和设计工程三方：
    • 系统工程负责试验需求和评价，试验工程负责实施试验和分析数据，设计工程负责试验设备；
    • 试验计划由系统工程与试验工程共同制订，测量项目由系统工程与设计工程共同确定，试验设备的需求由设计工程与试验工程共同提出；
    • 试验的总体架构由三方共同决定。
  • 管理层的关注格外强烈：试验中的每一次失败都会引起广泛注意，负责的人需要得到高层管理者的信任，并有权采取行动。

试验与评价的总体计划叫作试验与评价主计划（Test and Evaluation Master Plan），在概念探索结束时就要正式提出，以后每一步都要细化。但在实践中，它往往到工程设计阶段很晚的时候都还比较笼统，原因有三：

  • 试验的方法取决于系统元素在物理上怎样实现；
  • 早期的试验计划得到的人力和经费太少；
  • 模拟使用环境既复杂又昂贵。

主计划的正式格式包括五个部分：

  1. 系统介绍：任务、环境和效能度量；
  2. 综合试验计划概要：进度和参加的组织；
  3. 研制试验与评价：目标、方法和试验事件；
  4. 使用试验与评价：目标、构型、试验事件和情景；
  5. 试验与评价所需资源的汇总：试验品、试验场、测量仪器和保障。

从组件试验到使用试验

研制试验与评价由开发方在系统层面进行，要覆盖整个工作范围，用测试情景检验所有工作模式，消除所有性能缺陷。它同时也是使用试验的一次“预演”。在对设计、测试设备和测试计划都有很高把握之前，不应开始系统试验，因为试验一旦中途叫停，代价很高，还会招来管理层的审查。系统试验的配置要遵循几条原则：

  • 输入和环境：表现出所有的工作条件，包括与环境的相互作用；能用实物复制的尽量复制，其余的用模拟代替；实在无法在系统试验中复现的输入，例如超音速飞机遇到的雨，要另做专门的试验。
  • 输出和测试点：记录全部性能输出，同时记录输入和环境条件，以便相互对照；监测足够多的内部测试点，使偏差能够追查到来源。
  • 试验条件：尽量复现以后使用试验可能遇到的条件；有意让某些部分超负荷工作，检查系统能否“平稳降级”、恢复程序是否有效；请客户和评价机构的人员参加。

系统试验的结果要与系统性能模型的预测相比较。整个系统的行为太复杂，很难用一个模型完整再现，所以通常在两个层面分析：一是系统需求文件规定的端到端性能，二是某些关键行为在子系统或组件层面的表现；端到端的结果不符合预期时，后者是找到偏差来源的关键。

大型复杂系统还常常要专门造一台工程研制样机来做试验，它在外形、配合和功能上要尽量接近最终产品，所以造价和维护费用都很高，必须用它对整个项目的好处来证明值得。试验计划中还要有专门的安全部分，由安全工程师负责危险的运动部件、火工品、高电压、辐射和有毒材料等问题。

使用试验与评价由客户或独立的试验机构（例如美国海军的作战试验与评价部队）进行，对象是接近最终产品的预生产样机，环境与实际使用相同或非常接近。面向公众的产品还要经过监管机构的认证，例如客机的认证由美国联邦航空管理局负责。开发方的人员可以观察或提供支持，但在任何情况下都不能影响试验的实施或对结果的解释。使用试验最应优先关注四个方面：

  1. 新增的功能，往往是为了弥补前代系统的缺陷而加入的，这里的不确定性最大；
  2. 对环境的敏感性，这方面最不可能已经充分测试过；
  3. 与外部设备的互操作性，包括非标准的通信协议；
  4. 用户界面，包括培训需求、培训辅助手段、显示是否清楚和决策辅助。
例子：客机的使用试验

客机的使用试验几乎可以完全复现真实的运行：机组换成试飞机组，大多数乘客和行李用模拟物代替。困难在于恶劣天气，例如风切变，无法随时制造出来，只能用超负荷试验、风洞、特殊装备的机库和仿真来弥补。即便如此，客机也还算是“幸运”的情形，地面车辆的使用试验就需要专门挑选试验地形。

使用试验的结果通过三种报告提交：

  • 快报：重大试验事件之后立即发出，防止各方对结果作出错误的解读；
  • 状态报告：定期（例如每月）提交，试验结束时可能还有一份中期报告；
  • 最终评价报告：给出发现的问题、评价结论、关于系统是否适用的建议和需要的改进。

使用试验期间还要用仪器记录全部外部条件，作为评价的真值数据。

试验结果不符时，先查什么

在集成过程中观察到的故障，多数出自组件故障以外的原因：有缺陷的试验设备或试验程序、对规格的误解、定得不切实际的公差，或者人员的失误。公差就是一个例子：螺栓孔的公差定得太紧，制造时会有大量废品；定得太松，装配时又会配合不上。系统试验中出现的偏差可能来自六个方面：

  1. 试验设备
  2. 试验程序
  3. 试验的执行
  4. 对试验数据的分析
  5. 被试验的系统本身
  6. 偶尔还可能是某条需求定得过于严格

在对系统采取紧急修改之前，应当先排除前四种原因。时间总是很紧，很少有机会一条一条地排查，所以通常几条线索同时追查；系统内部许多测试点上的数据，能迅速缩小搜索范围。这也是试验程序必须在正式试验之前透彻理解、反复演练的原因。试验设备之所以常常出问题，有四个原因：

  • 它得到的设计投入比被测组件少得多；
  • 它的精度却必须比组件更高；
  • 组件级的测试设备和集成设施的设备在型号或校准上可能不一致；
  • 预测组件响应的模型本身也不完美。

如果问题确实出在被试验的系统上，先要判断它属于哪一种情况：

  • 轻微、容易纠正的；
  • 严重或者原因不明、需要推迟进度的；
  • 不严重，并且开发方和客户都同意推迟纠正的。

在这个阶段，重大的偏差很少能迅速纠正，因为任何设计修改都会引起设计文档、试验程序、接口规范和生产安排的一连串修改；有时可以改用别的办法消除偏差，例如用修改软件代替修改硬件。处理这类情况通常要组织一个攻关小组，尽快找到可以接受的解决办法。任何修改还会带来一个问题：已经通过的试验要不要重做，这对进度和费用影响很大，也要由系统工程判断。

如果系统的问题来不及在生产目标之前消除，而系统在其他方面适合使用，客户在详尽分析各种方案之后有两种选择：

  • 先有限度地放行生产，以后再把最初生产的系统改装到完全合格的设计；
  • 申请偏离许可，暂时或永久地允许系统偏离某项规格。

试验要做到多逼真

试验越逼真，结论越可信，但费用也越高，而且两者是收益递减的关系。

因此，“试验做到什么程度才够”是一个需要系统工程师权衡的决定。另外，人们常常低估试验系统的费用和周期。让试验人员尽早参与，最好在编写需求时就参与进来，可以保证写出来的需求是能够检验的。

试验的计划和准备

试验计划与系统开发有一一对应的关系：

  • 开发从“需要”出发确定要部署的能力，试验计划从“目标”出发确定试验项目需要多复杂；
  • 系统概念在性能、进度和费用之间权衡，试验概念在不同的试验方法、进度和费用之间权衡；
  • 功能设计把功能需求变成规格，试验计划把试验需求落实到每一个试验事件和它所需的资源；
  • 详细设计完成各个组件的设计，试验程序则为每一个试验事件写出详细的步骤并准备试验工具。

开始制订试验计划之前，要先复查需求是否变了。需求变化有三个来源：

  • 客户的需求：软件的修改看上去总是很容易，这种印象常常靠不住；
  • 技术的进步：在开发后期引入新技术很有诱惑力，风险也很大；
  • 项目计划，尤其是经费的不稳定。

试验计划中还有三个关键问题：

  • 试验失败会受到广泛关注，所以要收集足以解释失败原因的数据；
  • 开发阶段的超支常常挤占试验的预算；
  • 试验设备和设施要与系统同时建造，并尽量在研制试验和使用试验之间共用。

试验设备本身要满足三项标准，而且试验程序要在设计试验设备之前确定：

  • 精度：要比被测参数的公差高出好几倍，并有校准标准；
  • 可靠性：要靠自检监视或频繁的检查来保证；
  • 灵活性：一套设备能用于多种用途，但不能以牺牲精度或可靠性为代价。

常见的试验问题还有：

  • 保护数据的质量，保存并归档数据；
  • 让试验人员的技能跟上需要；
  • 校准工具，并保证试验设备不会使测量产生偏差；
  • 在两次试验之间保持试验品不变，不做“计划外的修补”，并对试验品实行构型控制；
  • 留出切合实际的时间；
  • 每条需求只写一项要求，避免把几项要求合写成一条；
  • 承认真实环境很难完全复现。

每一条需求用什么方法验证，记录在验证交叉引用矩阵（Verification Cross-Reference Matrix）中。验证方法有四种：试验、分析、演示和检查。

人因试验与体系试验

人机接口的性能取决于两点：操作人员受过的训练，以及接口本身的设计。以空中交通管制员为例，疲劳、别扭的控制器或难以辨认的符号都可能引起操作失误。人因试验包括人体工程（物理上的设计）和人的因素（人的能力和局限）两方面。常用的方法有：

  • 衡量剩余脑力的贝德福德工作负荷量表；
  • 访谈操作人员；
  • 眼动追踪；
  • 认知走查；
  • 用故障树分析找出执行任务时可能出错的地方，据此设计试验情景。

美国航天局在为水星、双子座和阿波罗飞行研制显示器和控制器时，就考虑了人与系统的接口。爱达荷国家实验室重新设计核电站控制室的显示器时，用三维模型做人因和人体工程分析，人体模型的尺寸从第 5 百分位的女性一直覆盖到第 95 百分位的男性。分析人为失误时要问的问题有：

  • 用户对这种配置满意吗？
  • 操作在完成之前中断了，会发生什么？
  • 有没有令人困惑的步骤？
  • 提供的信息是否充分、易懂？

好的人机接口工作负荷均衡、简单易用、能容忍失误、能提供指导和帮助，显示方式标准而一致。

体系的试验更为复杂。它要做到：

  • 尽早测试接口，优先测试风险高的系统间接口或体系的关键能力；
  • 跨项目测试接口规范和互操作性；
  • 由独立的一方验证和确认：验证体系在预定环境中是否符合体系的规格，确认它是否满足用户需要和任务目标。

体系试验还有一些悬而未决的问题：

  • 谁来主持试验？这可能取决于谁出钱最多，也可能取决于技术或组织上的因素。
  • 混在一起的试验数据归谁所有？
  • 其他系统的存在会不会使试验结果产生偏差？

此外，各方利益相关者相互竞争，没有一个权威能管辖所有系统，各个系统的升级时间也不同步。
